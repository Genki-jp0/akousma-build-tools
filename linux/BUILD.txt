Building Akousma on Linux
=========================

build-akousma.sh builds Akousma (https://github.com/Genki-jp0/Akousma) with the libraries of your distribution and
makes an install folder, an AppImage and, on request, a .deb or .rpm, for amd64, i386 and arm64 (see
"Architectures"). It is the Linux counterpart of
Build-Akousma.ps1 (Windows, BUILD.txt in the repository root): same idea of settings, folders, change detection,
--list, --dry-run and release locks, but no dependency is built, so a first build takes minutes, not hours.
The two scripts share nothing but the repository: each has its own settings file and its own release records.

In the repository root:
  build-akousma.sh            the script (bash; no other language needed)
  build-settings.linux.conf   your settings, created on the first run (not in git)
  versions/linux/             the package versions each Akousma release was built with (--freeze-deps)


Requirements
------------
bash 4.4 or newer, git, sudo (for --install-deps, and for an install folder that isn't writable), and one of:
  Debian 12+ / Ubuntu 24.04+      apt
  Fedora 43+                      dnf
  Arch Linux                      pacman
  openSUSE Tumbleweed / Leap 16   zypper
(the releases Akousma's CI builds). Akousma needs CMake 3.25+ and Qt 6.4+ (CMakeLists.txt); older distributions
don't have them.

The distribution is read from /etc/os-release (ID, ID_LIKE). Anything else: the script doesn't check packages, but
still builds when the libraries are there (install them by the lists in the script).

For the architectures other than the machine's own (see "Architectures"): podman or docker, and for arm64 on an
amd64 machine (or amd64 / i386 on an arm64 one) qemu-user with its binfmt_misc registration. --install-deps installs
them: podman (only when neither podman nor docker works) and
  apt     qemu-user-static          (Debian 12/13, Ubuntu 24.04+)
  dnf     qemu-user-static-aarch64  (qemu-user-static-x86 for amd64 / i386 on an arm64 machine)
  pacman  qemu-user-static qemu-user-static-binfmt
  zypper  qemu-linux-user
and then makes sure the handler is registered with the F flag (systemctl restart systemd-binfmt; without systemd, e.g.
in a container or WSL, the script writes /usr/lib/binfmt.d/qemu-<cpu>.conf to /proc/sys/fs/binfmt_misc/register
itself, adding F when the file lacks it). Docker needs its daemon running and your user in the docker group;
podman runs rootless and needs no setup.


Running it
----------
From the folder of the script (or anywhere: ./path/to/build-akousma.sh):

  ./build-akousma.sh --check-deps                 which packages are installed / missing; stops
  ./build-akousma.sh --install-deps               installs the missing ones (sudo; also podman and qemu-user-static
                                                  for the other architectures), then builds
  ./build-akousma.sh                              Akousma master for amd64, i386 and arm64: install folder + AppImage
  ./build-akousma.sh --arch amd64                 only amd64 (this run; --save-settings: from now on)
  ./build-akousma.sh --arch amd64,i386            amd64 and i386, one after the other
  ./build-akousma.sh --deb                        ... plus a .deb (apt systems)
  ./build-akousma.sh --rpm                        ... plus an .rpm (dnf / zypper systems)
  ./build-akousma.sh --native                     ... plus the package of this distribution (deb or rpm)
  ./build-akousma.sh --outputs install            only the install folder
  ./build-akousma.sh --ref v1.0.0                 a branch, tag or commit
  ./build-akousma.sh --source ~/src/Akousma       a local checkout, as it is (uncommitted changes included)
  ./build-akousma.sh --build-type debug           debug build, in its own folders
  ./build-akousma.sh --list                       what would be built and why; builds nothing
  ./build-akousma.sh --dry-run                    every resolved setting and folder, the source, the packages and the
                                                  CMake command of each architecture; changes nothing

Each run prints "Build settings: <file> (read / created with the defaults / saved ...)" first, then the architectures
and how each is built, then for each architecture ("==> [2/3] i386: container (docker.io/library/debian:trixie)") the
packages, the plan ("akousma: build (akousma changed 4a123cf -> 43804f0)", "appimage: skip (unchanged)") and the
steps. The output of each step goes to <build path>/logs/<step>.log (--verbose shows it too; the build shows its
progress in 10 % steps). On a failure the end of that log is printed with its path. Everything the script prints is
also appended to the run log (default ~/Atelier/data/projects/akousma/build_linux.log), the container builds' output
included. At the end: each architecture with ok / FAILED / not built and its time. --dry-run, --list and --check-deps
write no log.


Options
-------
Architectures (ARCHS, default amd64,i386,arm64; see "Architectures"):
  --arch LIST            comma-separated: amd64, i386, arm64 (also x86_64 / x64, i686 / x86, aarch64). Order kept.
  --container-engine E   podman, docker or auto (default): auto takes podman when "podman info" works, else docker.
  --container-image A=IMAGE
                         the base image of architecture A, repeatable (CONTAINER_IMAGES=i386=...,arm64=... in the
                         settings file). Default: see "Architectures".
  --container-arg ARG    an extra argument for "<engine> run" (the image setup and the build), repeatable; e.g.
                         --container-arg=--dns=192.168.1.1. Settings file: CONTAINER_ARGS, separated by spaces.
  --update-images        pull the base images again and make the build images again (the newest packages).

Akousma source:
  --repo URL             git URL, default https://github.com/Genki-jp0/Akousma.git. Cloned to <SRC_PATH>/akousma.
  --ref REF              branch, tag or commit, default master. Each run fetches (git fetch --prune --tags) and then
                         builds origin/<branch> for a branch, so it always builds the remote's newest commit. (A local
                         branch of the same name in the clone is never used: it would be stale.) Then a tag, then a
                         commit id. The clone is checked out detached at that commit; untracked files are removed,
                         ignored ones (files Akousma's CMake generates in the source tree) are kept.
  --source DIR           build a local checkout instead. Built out of tree; the checkout is not changed (except the
                         files Akousma's own CMake writes there: debian/changelog and dist/scripts/maketarball.sh,
                         both in its .gitignore). Its id for change detection is the commit plus a hash of the
                         uncommitted changes and untracked files, so editing a file rebuilds (incrementally).
                         The CMake build folder belongs to one source folder: switching between --source and the git
                         clone (or another checkout) in the same BUILD_PATH starts it again, a full build. Give a
                         checkout its own --build-path (and --prefix) to keep both builds incremental.
  --no-source            back to --repo / --ref (clears a saved AKOUSMA_SOURCE).
  --release REL          build the commit recorded in versions/linux/REL.txt (see "Release locks").

Build:
  --build-type TYPE      release (default), debug or relwithdebinfo (CMake Release / Debug / RelWithDebInfo).
  --jobs N               parallel jobs, default the number of CPUs.
  --werror, --no-werror  -DBUILD_WERROR=ON / OFF (default OFF: a newer compiler's new warnings don't stop the build).
                         The .deb always uses ON, as Akousma's debian/rules says; the .rpm too (its spec).
  --tests, --no-tests    build Akousma's tests (target build_tests) and run them with ctest (QT_QPA_PLATFORM=offscreen,
                         a temporary HOME). Default off. Also runs them in the .deb / .rpm build.
  --cmake-arg ARG        an extra CMake argument, repeatable: --cmake-arg -DENABLE_SPOTIFY=OFF. In the settings file:
                         CMAKE_ARGS=-DA=1 -DB=2 (separated by spaces, no quoting).
  --clean                delete the CMake build folder first: a full rebuild.
  --force                build and make every output even when nothing changed.

Outputs (OUTPUTS, default install,appimage):
  --outputs LIST         comma-separated: install, appimage, deb, rpm, native, none.
  --deb, --rpm, --native add that package to the outputs (for this run; with --save-settings, OUTPUTS is not
                         changed by these, use --outputs install,appimage,deb --save-settings).
  --no-appimage          leave the AppImage out.
  --update-tools         download linuxdeploy and its plugins again (they are "continuous" builds).

Dependencies:
  --check-deps           list the packages of the wanted outputs, installed or missing, with the install command;
                         for a container architecture the container setup and the image's packages (once the image
                         exists). Exit 1 when something is missing.
  --install-deps         install the missing packages: shows the command, then runs it with sudo (apt: apt-get update
                         first). Without it, a run with missing packages stops and prints the command. Also installs
                         and registers what the container architectures need (see "Requirements").
  --yes                  with --install-deps: no questions (apt-get -y, dnf -y, zypper -n, pacman --noconfirm).
  --freeze-deps REL      write versions/linux/REL.txt after the build of every architecture (with --dry-run: without
                         building). See "Release locks".

Folders (see "Folders"):
  --work-root DIR  --project-root DIR  --downloads-path DIR  --src-path DIR  --build-path DIR  --prefix DIR
  --output-path DIR  --tools-path DIR  --log-path FILE

Other:
  --settings FILE        another settings file than build-settings.linux.conf next to the script.
  --save-settings        write the settings given on this command line into the settings file (paths absolute).
  --list, --dry-run, --verbose, -h / --help


Build settings
--------------
build-settings.linux.conf keeps: ARCHS, WORK_ROOT, PROJECT_ROOT, DOWNLOADS_PATH, SRC_PATH, BUILD_PATH, PREFIX_PATH,
OUTPUT_PATH, TOOLS_PATH, LOG_PATH, AKOUSMA_REPO, AKOUSMA_REF, AKOUSMA_SOURCE, BUILD_TYPE, OUTPUTS, JOBS, WERROR, TESTS,
CMAKE_ARGS, CONTAINER_ENGINE, CONTAINER_IMAGES, CONTAINER_ARGS. (Windows' Build-Akousma.ps1 has its own
build-settings.json; the two files are independent.) An older file without the new keys gets the defaults for them
(all three architectures); --save-settings adds the keys that are missing.
The first run creates it with the defaults (with a comment per line). For each setting the command line wins, then
the file, then the default (a line missing from the file = the default). Command-line options are for that run only;
--save-settings writes them into the file, keeping your other lines and comments:

  ./build-akousma.sh --ref my-branch                         this run only
  ./build-akousma.sh --ref my-branch --save-settings         now and from now on
  ./build-akousma.sh --arch amd64 --save-settings --dry-run  only amd64 from now on (ARCHS=amd64)
  ./build-akousma.sh --src-path /mnt/data/src --save-settings --dry-run    save without building

The file is KEY=value, one per line, # for comments, optional quotes around a value. It is parsed, never run (no
"source"): there is no shell expansion except a leading ~ and the placeholders. Unknown keys are reported and ignored.
Delete a line or the whole file to get the defaults back.


Folders
-------
Defaults (placeholders as in the file; each location may use the ones before it):

  WORK_ROOT       ~/Atelier
  PROJECT_ROOT    {WORK_ROOT}/data/projects/akousma
  DOWNLOADS_PATH  {PROJECT_ROOT}/linux_/downloads
  SRC_PATH        {DOWNLOADS_PATH}                       git clones: akousma, kdsingleapplication
  BUILD_PATH      {PROJECT_ROOT}/linux_/build_{ARCH}_{BUILD_TYPE}
  PREFIX_PATH     {WORK_ROOT}/akousma_linux_{ARCH}_{BUILD_TYPE}     the install folder
  OUTPUT_PATH     {BUILD_PATH}/packages                  AppImage, .deb, .rpm
  TOOLS_PATH      {PROJECT_ROOT}/linux_/tools            linuxdeploy-<arch>.AppImage and its plugins
  LOG_PATH        {PROJECT_ROOT}/build_linux.log

{ARCH} is the architecture being built, by the names AppImages use: x86_64 (amd64), i686 (i386), aarch64 (arm64);
{BUILD_TYPE} the build type. A location still at its default follows the ones it is made of, so
WORK_ROOT=/mnt/fast/Atelier moves everything. Downloads, the git clones and the AppImage tools are shared by the
architectures; each has its own build tree (with its packages folder) and install folder. A BUILD_PATH or PREFIX_PATH
you set without {ARCH} is the machine's own architecture's; the others get _<arch> appended (/mnt/build ->
/mnt/build_i686) unless the folder name says the architecture already, so they never build into the same folder.
An OUTPUT_PATH without {ARCH} is shared: the file names say the architecture. To keep the sources on another drive:
--src-path /mnt/data/akousma/src (and --downloads-path) with --save-settings.

Inside BUILD_PATH:
  akousma/        the CMake build folder (akousma binary: akousma/akousma)
  deps/           KDSingleApplication, when it is built from source
  logs/           one log per step (configure.log, build.log, appimage-linuxdeploy.log, deb-build.log, ...)
  stamps/         change detection
  appimage/       AppDir and the staged GStreamer plugins
  deb/akousma/    the copy of the source dpkg-buildpackage builds in (keeps its obj-* folder between runs)
  rpmbuild/       rpmbuild's _topdir
  home/           HOME of a container build

The install folder (PREFIX_PATH) is deleted and installed again by each build, so files Akousma doesn't install any
more don't stay behind; the script only deletes it when it made it (marker file .akousma-build-tools). An install
folder that isn't writable (e.g. --prefix /usr/local) is installed with sudo and not deleted first. To start the
installed build: ~/Atelier/akousma_linux_x86_64_release/bin/akousma. It uses the distribution's libraries, so it runs
on this system only. The install folder of a container architecture uses the image's libraries: it runs in that
image (or a system of the same distribution release and architecture); ship the AppImage or the package instead.


Packages (dependencies)
-----------------------
The package lists are in the script (PKGS[...]), per package manager and group:
  build      always: compilers, CMake, ninja, Qt 6 (base, private headers, tools, linguist), GStreamer, TagLib, ICU,
             ... everything Akousma's CMakeLists.txt finds, the optional components included (Akousma's CMake stops
             when an optional feature that is on by default misses its library, cmake/OptionalComponent.cmake)
  runtime    always: Qt's SQLite driver and platform plugins, GStreamer base/good (+ ALSA / PulseAudio output)
  tests      --tests: gtest, gmock
  deb        a .deb: debhelper, dpkg-dev, fakeroot, lsb-release
  rpm        an .rpm: rpm-build, the tools the spec's BuildRequires name (desktop-file-utils, appstream-glib, gtest)
  appimage   an AppImage: curl, patchelf, file, desktop-file-utils, GStreamer bad/ugly/libav (more formats in the
             AppImage), Qt SVG and Wayland
Where the names come from (also in the script's comments):
  apt     Akousma's debian/control and the Ubuntu / Debian jobs of its .github/workflows/build.yaml
  dnf     the Fedora job of build.yaml and dist/unix/akousma.spec.in
  zypper  the openSUSE and AppImage jobs of build.yaml and the spec
  pacman  Arch Linux's strawberry PKGBUILD (1.2.31), plus what Akousma's CMake finds besides
An entry "a|b" is the first one that exists (libtag-dev on newer Debian/Ubuntu, libtag1-dev on older). Version checks
(apt): libkdsingleapplication-qt6-dev must be 1.1.0 or newer, else KDSingleApplication is built from source;
liblayershellqtinterface-dev must be the Qt 6 one (6.x), else it isn't used.

Switched off automatically (shown as "note:"; --cmake-arg can switch them on again):
  -DENABLE_LAYERSHELLQT=OFF   when LayerShellQt for Qt 6 is not installed, or Qt is older than 6.5 (no
                              QWaylandApplication). Same rule as Akousma's debian/rules and spec.

KDSingleApplication from source: when the distribution's KDSingleApplication-qt6 is missing or older than 1.1.0
(Ubuntu 24.04: 1.0.0), the script clones https://github.com/KDAB/KDSingleApplication to <SRC_PATH>/kdsingleapplication,
builds v1.2.1 as a static library into <BUILD_PATH>/deps and passes it to Akousma (CMAKE_PREFIX_PATH; also to the
.deb build). Static, as in upstream Strawberry's Ubuntu CI, so nothing extra is needed at run time. Rebuilt when its
commit or the Qt package version changes.


Architectures
-------------
ARCHS (--arch) lists the architectures to build, by their Debian names: amd64, i386 and arm64 by default, like
Build-Akousma.ps1's x64, x86 and arm64. They are built one after the other, in the order given, each in its own
folders. The run of each is the same script with the same settings and options (--arch-build <arch>, internal), and
every one builds the same Akousma commit: the run you start resolves (and fetches) it once.

The machine's own architecture (uname -m) is built natively, as described in the rest of this file. Each other one is
built in a container, because a distribution's packages only exist for its own architecture on its own release:
  - the script makes a build image per architecture once, localhost/akousma-build:<arch>-<base image>: it pulls the
    base image for that platform (podman/docker pull --platform linux/386 or linux/arm64), checks that its programs
    run here, runs itself in it as root with --image-setup (installs every package group of that distribution: build,
    runtime, tests, appimage and deb or rpm, as --install-deps would) and commits the container. The image is made
    again when the base image or the package lists in the script change, or with --update-images (newest packages).
    Like on the machine itself, the packages in an image are only updated when you ask for it; a new image changes
    the package versions, so the next build rebuilds (see "Change detection").
  - then it runs the build in a new container of that image: "<engine> run --rm --platform ... --network host
    --security-opt label=disable" with every folder the build uses mounted at the same path (the build tree, install
    folder, packages folder, tools, git clones, --source; the script's folder and the settings file read-only), so
    paths, stamps and logs are the same inside and out. It runs as you (podman: --userns=keep-id; docker: --user
    <uid>:<gid>), so the files it makes are yours; HOME is <build path>/home. The proxy variables (http_proxy, ...)
    are passed in; --container-arg adds anything else (a CA certificate, --dns, ...). i386 runs under "setarch i686",
    so uname -m says i686 as CMake and the AppImage tools expect. Ctrl-C stops the container.
How each architecture's programs run on the machine:
  i386 on amd64     natively (an amd64 kernel runs 32-bit programs): about as fast as the amd64 build
  arm64 on amd64    qemu-user (qemu-aarch64 via binfmt_misc, F flag): every compiler run is emulated, roughly 5 to 10
                    times slower; a first build takes hours, later ones only recompile what changed
  amd64, i386 on arm64   qemu-user (qemu-x86_64, qemu-i386), the same way
The base images (CONTAINER_IMAGES or --container-image arch=image chooses another):
  this machine          i386                                 the other one(s)
  Debian 12/13 (...)    docker.io/library/debian:<codename>  docker.io/library/debian:<codename>
  Ubuntu 24.04 (...)    docker.io/library/debian:trixie      docker.io/library/ubuntu:<VERSION_ID>
  Fedora 43 (...)       docker.io/library/debian:trixie      registry.fedoraproject.org/fedora:<VERSION_ID>
  openSUSE Tumbleweed   docker.io/library/debian:trixie      registry.opensuse.org/opensuse/tumbleweed:latest
  anything else         docker.io/library/debian:trixie      docker.io/library/debian:trixie
The other architectures get the machine's distribution release where it has an image for them, so their packages and
outputs match the machine's build (a Fedora machine gets an aarch64 .rpm). i386 always gets Debian, because:
  - Debian 13 (trixie) still builds every package Akousma needs for i386: Qt 6.8.2, KDSingleApplication 1.1.0,
    LayerShellQt 6.3, TagLib 2.0, GStreamer 1.26, CMake 3.31, gtest (checked 2026-11 in a linux/386 trixie container).
    Debian 12 (bookworm) has Qt 6.4.2 for i386 (Akousma's minimum) but KDSingleApplication only from source.
  - Ubuntu has no i386 Qt 6 and no i386 image; Fedora has no i686 image (its i686 packages are multilib only); the
    Arch Linux image is amd64 only, openSUSE has no i586 Tumbleweed image.
Why containers, not cross-compiling: Debian's multiarch could cross-compile on a Debian machine, but only on Debian of
the same release, and the AppImage tools (linuxdeploy and its Qt plugin) have to run the target architecture's
programs anyway. Containers work the same on every distribution, need no root (podman) and leave the machine's
packages alone.

Outputs: each architecture makes the outputs of OUTPUTS: install folder, AppImage (Akousma-<version>-i686.AppImage,
...-aarch64.AppImage; with the AppImage tools of that architecture), and .deb / .rpm when its distribution can make
them. An output its distribution can't make is left out for that architecture only, with a WARNING (".deb packages
are made on Debian / Ubuntu ..."), and the summary says so ("ok (not made here: rpm)"): e.g. --rpm on Fedora gives an
x86_64 and an aarch64 .rpm but no i686 one (there is no i686 Fedora); --deb on Fedora gives the i386 .deb only.
--native is the package format of the distribution each architecture is built on.

When an architecture can't be built: before building, the script checks the container engine ("podman info" /
"docker info") and, for each architecture that needs qemu, its binfmt_misc handler. An architecture whose
prerequisite is missing is not tried (the others are built), and so is one whose image can't be made (the base image
can't be pulled, or its programs don't run: "exec format error"). The run then ends with exit code 1: a summary that
names each architecture that wasn't built and why, the command that fixes it (--install-deps, and what it runs), and
"--arch <this machine's> builds only this machine's architecture". This is an error, not a warning, on purpose: the
default is all three, and a run that quietly made only amd64 would look like a complete release. --dry-run and --list
show the same problems but end with 0; --check-deps ends with 1.


Change detection
----------------
<BUILD_PATH>/stamps/build.stamp records what the last successful build was made of:
  akousma   the Akousma commit (a local checkout: commit + hash of the uncommitted changes)
  config    the CMake arguments (build type, prefix, Werror, auto and extra args, generator), tests on/off
  deps      the versions of the build / runtime / tests packages
When all three are unchanged and the build folder has its akousma binary, the build is skipped ("akousma: skip
(unchanged ...)"). Otherwise the reasons are printed ("akousma changed 4a123cf -> 43804f0", "settings changed:
-DBUILD_WERROR=OFF -> -DBUILD_WERROR=ON", "packages changed: qt6-base-dev 6.4.2+dfsg-21.1build5 -> ..."), and CMake
configures and builds again in the same folder, so only what changed is recompiled. A changed package version
re-runs CMake too (an updated Qt may need it).
Each output has its own stamp (stamps/<output>.stamp): it is made again when the build changed, when its file is gone,
or when its own inputs changed (the install folder path; the AppImage tools; tests for the packages). So adding --deb
to an unchanged build only makes the .deb.
  --list     shows this decision for every step, builds nothing
  --force    builds and makes the outputs anyway (CMake still only recompiles what changed)
  --clean    deletes the CMake build folder first
A failed build leaves no stamp, so the next run builds again.
Each architecture has its own stamps (in its build tree) and is decided on its own: the packages of a container
architecture are the ones in its image, so a new image (--update-images) rebuilds that architecture only.


AppImage
--------
Made with linuxdeploy (https://github.com/linuxdeploy/linuxdeploy), linuxdeploy-plugin-qt and
linuxdeploy-plugin-gstreamer, downloaded into TOOLS_PATH the first time (--update-tools: again):
  linuxdeploy-<arch>.AppImage            .../linuxdeploy/releases/download/continuous/
  linuxdeploy-plugin-qt-<arch>.AppImage  .../linuxdeploy-plugin-qt/releases/download/continuous/
  linuxdeploy-plugin-gstreamer.sh        raw.githubusercontent.com/linuxdeploy/linuxdeploy-plugin-gstreamer/master/
<arch> is x86_64, i386 or aarch64 (linuxdeploy's names; the AppImage itself is named x86_64, i686 or aarch64). The
tools of a container architecture run in its container (arm64 under qemu). The linuxdeploy AppImage contains the
AppImage output plugin and appimagetool. To use other builds of these tools,
put them into TOOLS_PATH under these names (the script doesn't download a file that is there).
Steps:
  1. cmake --install into <BUILD_PATH>/appimage/AppDir/usr (a separate install with prefix /usr inside the AppDir).
  2. GStreamer: the plugins of upstream Strawberry's AppImage list (build.yaml, build-appimage) that are installed are
     staged (symlinks) and handed to the gstreamer plugin, which copies them, bundles their libraries, sets their
     rpath and adds an AppRun hook (GST_PLUGIN_PATH, gst-plugin-scanner). Plugins that aren't installed are listed
     ("not installed, left out: faac fdkaac ..."); install more GStreamer packages to get them. The distribution's
     codecs end up in the AppImage: mind their licenses before you publish it.
  3. linuxdeploy --appdir ... --desktop-file io.github.genki_jp0.Akousma.desktop --icon-file akousma.png
     --plugin qt --plugin gstreamer --output appimage, with QMAKE=<Qt 6 qmake>, EXTRA_QT_MODULES=svg (when Qt SVG is
     installed), EXTRA_PLATFORM_PLUGINS=the Wayland platform plugin (when installed), APPIMAGE_EXTRACT_AND_RUN=1 (the
     tools run without FUSE) and LINUXDEPLOY_OUTPUT_VERSION=<Akousma version>.
  4. The result goes to OUTPUT_PATH/Akousma-<version>-<arch>.AppImage.
An AppImage only runs on distributions with a glibc at least as new as the one it was built on: build releases on
the oldest distribution you want to support.


.deb (Debian / Ubuntu)
----------------------
Made with Akousma's own debian/ folder, like its CI ("make deb": dpkg-buildpackage -b -d -uc -us -nc):
  1. The source is copied to <BUILD_PATH>/deb/akousma (git's tracked and untracked-not-ignored files; never built in
     your checkout). Its obj-<triplet> build folder is kept between runs, so rebuilds are incremental.
  2. debian/changelog is made from debian/changelog.in (version from Akousma's CMake, the distribution's codename and
     the date), as Akousma's debian/CMakeLists.txt does.
  3. DEB_BUILD_OPTIONS="nocheck parallel=N" (without nocheck with --tests) dpkg-buildpackage -b -uc -us -nc -d -jN.
     -d because the script checked the dependencies itself (Build-Depends names a KDSingleApplication that is built
     from source on Ubuntu 24.04; CMAKE_PREFIX_PATH points the build at it).
  4. akousma_<version>-<codename>_<arch>.deb (and the -dbgsym .ddeb) go to OUTPUT_PATH.
Install it with: sudo apt install ./akousma_<version>-<codename>_amd64.deb


.rpm (Fedora / openSUSE)
------------------------
Made with Akousma's dist/unix/akousma.spec.in, like its "rpm" CMake target and its CI:
  1. Akousma's CMake writes <build>/akousma.spec when lsb_release and rpmbuild are installed (the rpm group).
  2. dist/scripts/maketarball.sh makes akousma-<version>.tar.xz into <BUILD_PATH>/rpmbuild/SOURCES.
  3. rpmbuild -bb --nocheck (without --nocheck with --tests) --define "_topdir <BUILD_PATH>/rpmbuild".
  4. The .rpm files go to OUTPUT_PATH.
Two mistakes in Akousma's spec.in make rpmbuild fail; the script fixes them in its copy of the spec and prints a
WARNING for each (the fixes belong in Akousma's dist/unix/akousma.spec.in):
  - %files names *.appdata.xml, but Akousma installs io.github.genki_jp0.Akousma.metainfo.xml ("File not found").
  - %files has no line for share/akousma (the icon sets, iconsets/*.rcc) ("Installed (but unpackaged) file(s)
    found"); the script adds %{_datadir}/akousma/.
The rpm group installs "which" too: maketarball.sh looks for tar with it, and Fedora's container image has no which.
Install it with: sudo dnf install ./akousma-<version>-1.fc43.x86_64.rpm


Release locks (versions/linux/)
-------------------------------
Distribution packages can't be pinned: the package manager installs what the distribution ships today, and most
distributions don't keep old versions. So a release lock records instead of pins:

  ./build-akousma.sh --ref v1.0.0 --freeze-deps 1.0.0             build 1.0.0 and write versions/linux/1.0.0.txt
  ./build-akousma.sh --ref v1.0.0 --freeze-deps 1.0.0 --dry-run   only write the file (no build)
  ./build-akousma.sh --ref v1.0.0                                 later: 1.0.0 again
  ./build-akousma.sh --release 1.0.0                              the same, by the lock's name

versions/linux/<release>.txt (KEY=value) holds akousma_commit, the build tools commit, the date and archs (the
architectures it covers), then one section per architecture, its keys prefixed with the architecture
(amd64.distro=ubuntu, i386.pkg.qt6-base-dev=6.8.2+dfsg-9+deb13u2): the distribution (ID, VERSION_ID, PRETTY_NAME) it
was built on, the container base image and its digest (container architectures), the package manager, build type and
CMake arguments, the KDSingleApplication tag and commit when it was built from source, the sha256 of the AppImage
tools, and pkg.<name>=<version> for every dependency package that was installed (in the image, for a container
architecture). Each architecture's run writes its section to <build path>/stamps/freeze-<release>.part; the run you
started writes the file when every architecture of ARCHS was built (else it says which weren't and writes nothing:
build them, or freeze with --arch naming the ones the release has). An existing file is never replaced (delete it to
freeze again). A release with uncommitted local changes can't be frozen. A lock without sections (one architecture,
from before) is read as the section of its arch=.

A lock is used when: --release REL; --ref REL or --ref vREL and versions/linux/REL.txt exists; or the commit being
built is the one a lock records. Then the script, for each architecture,
  - builds the lock's akousma_commit (if the tag points elsewhere now, it warns and still builds the recorded commit),
  - builds the recorded KDSingleApplication tag (when it comes from source),
  - warns when the distribution or its version differs from the lock's,
  - compares every pkg.<name> of its section with what is installed (in its image) and warns about each difference
    ("package qt6-base-dev: 6.4.2+dfsg-21.1build6 now, 6.4.2+dfsg-21.1build5 in the lock"),
  - warns when the lock has no section for it (and still builds the lock's commit).
It does not downgrade packages and does not stop. For a build that matches a release exactly, keep a container or VM
of the distribution release it was frozen on; for binaries that run on many distributions, ship the AppImage.
